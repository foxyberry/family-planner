드라이버 기준은 `feature/driver-server`의 `e9814de`입니다. `626ec05`가 디버그 앱의 `ls`·`do` 서버와 Python CLI를 추가했고, `e9814de`가 실기기용 메모리 테스트 모드를 추가했습니다. 기존 `wt-p3`의 Bazel 로그에는 AppCore 49개, DebugTools 35개, Journeys 13개가 각각 실패 0개로 기록돼 있었습니다.

                      v              v

                       v            v

## 제안하는 변경과 완료 조건

### 1. Bazel 테스트와 실행 앱에 같은 기본 fixture 제공

- `WorldData`의 표준 학교·버스 fixture와 실기기 테스트 모드가 공유할 최소 데이터 정의를 검토합니다. 가변 상태와 시나리오별 덮어쓰기는 각 실행에 둘 수 있습니다. 선택할 학교 ID나 정류장 코드를 한쪽에만 추가하면 다른 쪽에서도 알아차릴 수 있어야 합니다.
- 메모리 저장소에서 두 Journey가 사용하는 동작의 의미를 맞춥니다. 새 ID 저장은 추가하고, 기존 ID 저장은 같은 위치에서 교체해야 합니다. 이 동작을 공통 구현으로 두는 편이 맞는지, 두 구현이 필요하다면 계약 테스트로 확인할지 검토합니다. SwiftData 저장과 재실행 후 복원은 Live 저장소 테스트에서 검증합니다.
- `Driver/PROTOCOL.md`에 Bazel `World`와 앱 테스트 모드 각각의 데이터 주입 위치와 교체하는 클라이언트를 적습니다. 의존성이나 fixture가 빠졌을 때는 가능한 한 화면 타임아웃이나 일반적인 액션 거절보다 원인에 가까운 메시지를 남깁니다.

**완료 조건**은 같은 `first-run.json`과 `add-a-child.json`이 Bazel과 USB iPad에서 모두 통과하고, 학교 fixture를 빼거나 새 ID 추가를 되돌리면 관련 테스트가 의도한 지점에서 실패하는 것입니다.

### 2. 실기기 실행을 재현 가능하게 만들기

- `e9814de`에서 `make -n ui-test DEVICE=1`은 시뮬레이터 명령을 출력합니다. 실기기 JSON 재생은 `make device`로 설치한 디버그 앱과 USB 포워딩으로 실행했습니다. 두 실행 경로의 명령을 문서에서 정확히 구분합니다.
- `devicectl device process launch`에서 앱 플래그 앞에 인자 구분자 `--`가 필요했습니다. 각 Journey를 시작하기 전 USB에서 `ls`가 연결되고 기대한 시작 화면이 보일 때까지 기다립니다. 즉시 요청했을 때 재실행 중 연결이 끊긴 사례가 있었고, 시작 상태를 기다린 같은 실행에서 두 Journey가 연속 통과했습니다.
- 이번에는 설치에 유효한 프로파일이 남아 있었지만, 만료까지 24시간 미만이라 저장소 스크립트가 갱신을 요구했습니다. 임시 복사본에서만 여유 기준을 조정해 설치했습니다. 프로파일 갱신 정책은 하네스 수정 제안과 별도로 판단할 수 있습니다.

**완료 조건**은 고정된 커밋과 테스트 모드 인자를 남기고, 테스트 데이터에서 시작한 것이 확인된 뒤에만 재생하는 것입니다. 실패하면 설치·실행·USB 연결·Journey 검증 중 어느 단계에서 멈췄는지 알 수 있어야 합니다.

### 3. 네트워크 경계의 검증 수준 결정

Family Planner의 앱 동작 테스트는 TCA의 `DependencyValues`에서 클라이언트를 교체할 수 있습니다. HTTP 요청, 응답 파싱, 오류 처리를 검사하려면 `BusClient.live(key:session:)`의 `URLSession` 인자를 별도 테스트에 사용할 수 있습니다. 이번 두 Journey는 클라이언트 수준의 fixture로 실행했습니다.

Shopify Reflex는 앱 Core 생성자에 플랫폼 의존성을 넘기고 테스트에서 네트워크·기기 경계에 fixture를 제공합니다. 또한 행동 테스트 중 예상치 못한 HTTP 요청을 실패로 처리합니다. 우리 프로젝트에서는 우선 현재 테스트 모드의 외부 클라이언트가 어떻게 연결되는지 명시하고, 같은 종류의 누락이 반복되면 허용된 로컬 드라이버 연결과 외부 서비스 요청을 구분해 실패시키는 검증을 검토할 수 있습니다. [Shopify Engineering Reflex](https://shopify.engineering/reflex)

## 실행 근거

분리 복사본에서 실행한 Bazel 명령과 결과입니다.

```text
make test-one PUBLIC_BUILD=1 \
  TARGET='//ios/DebugTools/Tests:DebugToolsTests //ios/AppCore/Tests:AppCoreTests //ios/Journeys/Tests:Journeys' \
  TEST_ARGS='--nocache_test_results --local_test_jobs=1'

Executed 3 out of 3 tests: 3 tests pass.
```

서명 빌드는 `make device PUBLIC_BUILD=1 DRIVER=1 FAMILY=empty NOW=2026-11-10T07:30 SKIP_FACE_ID=1`로 설치했습니다. iPad의 드라이버 포트 8790을 USB로 전달하고, 각 Journey에 맞춰 `empty` 또는 `sample`로 앱을 다시 시작한 뒤 실행했습니다. 예시 날짜와 가족 데이터는 fixture입니다.

```text
python3 tools/driver/fp-driver.py run ios/Journeys/Tests/Driver/journeys/first-run.json
first-run: journey passed

python3 tools/driver/fp-driver.py run ios/Journeys/Tests/Driver/journeys/add-a-child.json
add-a-child: journey passed
```

이 실기기 검증은 앱이 실행 중인 상태에서 실제 reducer, 저장 후 갱신, 화면 전환을 포함합니다. 드라이버가 액션을 직접 보내므로 실제 길게 누르기, 키보드 포커스, 버튼 발견 가능성은 별도 검증이 필요합니다. 테스트 모드는 메모리 저장소를 사용하므로 디스크 저장 후 재실행 복원도 별도입니다.

## 변이 테스트로 검출력 확인

### 실행한 실험

로컬 `develop`의 `b5a0cce`에서 원본 테스트 타깃 세 개가 통과하는 것을 확인했습니다. 임시 복사본에 고정한 변이 7개를 하나씩 적용해 관련 타깃을 재실행했고, **기존 테스트는 6개를 검출했습니다.** 패치 복원 뒤 원본 타깃 세 개가 다시 통과했습니다.

| 일부러 넣은 동작 변경 | 검출한 테스트 |
|---|---|
| 정확한 일정 시작 시각에 현재 일정이 표시되지 않음 | 미검출 |
| 일정 종료 시각에도 현재 일정으로 표시 | `DayPlannerTests` |
| 루틴이 적용 시작일 당일에는 적용되지 않음 | `DayPlannerTests` |
| 건너뛴 날짜에도 반복 일정이 표시됨 | `DayPlannerTests`, `SeriesEditsTests` |
| 끝난 일정을 다음 반복 일정으로 선택 | `SeriesEditsTests` |
| 120초 대신 119초에 보호자 화면을 잠금 | `ParentLockTests`에서 검출, Journey는 통과 |
| 아이를 저장한 뒤 홈 갱신을 생략 | `FamilyJourneys`에서 검출, `AppCoreTests`는 통과 |

일정 시작 경계에서 `DayPlannerTests.testNowAndNext`에 시작 시각 검증 한 줄을 임시로 추가하니 **원본은 통과하고 변이만 실패**했습니다. 이 실험은 미래에 해당 회귀가 생겼을 때 모델 테스트가 놓칠 수 있음을 보여줍니다. 실제 홈 화면이 그 시각에 갱신되는지는 별도의 Journey에서 확인할 수 있습니다.

### 하네스에서 쓸 방법

- 변경된 제품 규칙에 대해 비교 연산자나 호출 누락 같은 변이 몇 개를 고릅니다. 고정 규칙은 생성부터 결정적으로 만들 수 있습니다. LLM이 문맥을 읽어 고른 변이는 패치와 대상 타깃을 저장한 뒤 같은 입력으로 재실행합니다.
- 기존 테스트를 통과한 변이는 스펙이 기대하는 관찰 가능한 결과와 비교합니다. 원본 통과와 변이에서의 관련 assertion 실패가 확인되면 회귀 검증을 남깁니다. 빌드 오류나 무관한 타임아웃은 검출에서 제외합니다.
- 당장은 PR에서 몇 개의 관련 변이를 실행하고 어떤 규칙을 검증했는지 기록합니다. 중요한 공백이 반복해서 발견되면 같은 변이 집합을 재생하는 러너를 검토합니다. 이번의 `6/7`은 선택한 일곱 가지의 결과입니다. 변이 검출과 실제 결함 검출의 연관성이 관찰됐지만, 연구 대상 실제 결함의 27%는 일반적인 변이 연산자로 만든 변이와 연결되지 않았습니다. [실제 결함과 변이 비교, FSE 2014](https://homes.cs.washington.edu/~rjust/publ/mutants_real_faults_fse_2014.pdf)
- 살아남은 변이를 다음 테스트 작성에 되돌리는 방식은 MUTGEN에서 평가됐습니다. 기존 테스트를 보여주고 그 테스트가 놓칠 만한 잘못된 구현을 생성하는 방법도 두 코딩 벤치마크에서 평가됐습니다. Family Planner에서는 우선 빠져나간 변이의 목록과 근거를 리뷰에 쓰고, 전체 합격 점수 도입은 효과를 확인한 뒤 판단합니다. [MUTGEN](https://arxiv.org/abs/2506.02954) · [테스트를 겨냥한 변이 생성, ESEM 2026](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.49)

## 아이 모드와 보호자 모드 사이의 UX 검증

### 평가할 흐름

**보호자가 반복 일정을 내일부터 변경하고, 다음 날 아이가 홈에서 자기 할 일을 알아내는 과제**를 제안합니다. 이 과제의 UX 평가는 아직 실행하지 않았습니다. 먼저 디자인 세션이 적용 기준으로 삼는 보드 버전과 해당 M2 스펙을 확인합니다.

| 평가 질문 | 방법과 관찰할 결과 |
|---|---|
| 설계가 충분히 정의됐는가 | 보드만 보고 진입 → 편집 → 변경 범위 선택 → 저장 → 아이 홈을 따라갑니다. 단계별 화면 단서와 기대 결과를 적고 스펙과 대조합니다. 예를 들어 저장 직후 아이 홈 반영 시점과 편집 중 잠겼을 때의 초안 처리가 정의돼 있는지 확인합니다. |
| 두 모드의 목표가 충돌하는가 | 화면만 보고 보호자가 편집 진입점과 변경 범위를 찾을 수 있는지 검토합니다. iPad에서 첫 행동, 잘못된 날짜에 저장했는지, 아이가 도움 없이 다음 할 일을 맞혔는지를 관찰합니다. |
| 더 나은 설계가 있는가 | 같은 과제로 현재 시계 중심 편집과, 보호자가 목록에서 날짜 범위를 먼저 정하고 시계에서 결과를 미리 보는 대안을 비교합니다. 저장 전에 의도한 변경 범위를 설명할 수 있는지와 도움 요청을 관찰합니다. 대안의 효과는 관찰 전 가설로 둡니다. |

LLM은 보드와 스펙에서 단서가 약하거나 결정이 빠진 지점을 찾고 비교안을 만드는 데 사용합니다. 자동 목업 리뷰 연구에서 전문가가 제안의 일부를 정확하거나 부분적으로 정확하다고 평가했고, UXCascade는 에이전트의 행동 기록을 모아 수정 전후를 다시 평가했습니다. 모델과 사람의 선호가 평가 항목에 따라 어긋난 사례도 보고됐으므로, 아이의 이해와 선호는 실제 사용 관찰로 판단합니다. [자동 목업 리뷰, CHI 2024](https://people.eecs.berkeley.edu/~bjoern/papers/duan-heuristic-chi2024.pdf) · [UXCascade, UIST 2026](https://www.steffenholter.com/papers/uxcascade.pdf) · [MLLM as a UI Judge](https://arxiv.org/abs/2510.08783)

### 현재 도구로 남길 결과물

1. **흐름도와 UX 리뷰**에는 사용자 목표, 보드 버전, 막힌 단계의 화면 근거, 비교안, 어떤 관찰 결과가 설계 결정을 바꿀지를 남깁니다. 화면 단서로 찾는 능력을 볼 때는 Driver의 액션 목록을 제공하지 않습니다.
2. **Swift Journey**에는 합의한 동작을 넣습니다. 과거 일정은 유지되고 변경일부터 새 일정이 아이 홈에 나타나는지 확인합니다. 현재 USB Driver 계약에는 Our Day 편집과 시간 전진이 빠져 있어, 실기기 JSON 재생까지 필요할 때 해당 액션과 관찰 필드를 확장합니다.
3. **스냅샷과 UI 테스트**는 배치와 실제 길게 누르기, 키보드 포커스를 확인합니다. 누가 도움 없이 흐름을 이해했는지와 어느 대안이 나았는지는 iPad에서 같은 과제를 수행한 관찰 기록으로 남깁니다.

### 업계에서 쓰는 기준

코딩 에이전트의 L3·L4에는 공통 합격선이 없습니다. 아래 분류는 같은 숫자를 쓰더라도 책임의 범위를 다르게 정합니다.

| 분류 | L3 | L4 |
|---|---|---|
| Dan Shapiro의 코딩 자율성 분류 | 에이전트가 구현하고 사람이 진행 중 코드를 리뷰합니다. | 사람이 스펙과 계획을 정하고 에이전트가 실행합니다. 사람은 이후 결과와 테스트를 확인합니다. [Shapiro 원문](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/) |
| LACG의 자동화 분류 | 에이전트가 수정·검증·재시도하고 해결하지 못한 실패는 사람이 맡습니다. | 정의된 범위에서 에이전트가 검증과 통합을 마무리하고, 실패하면 스스로 안전한 상태로 복구합니다. 이 연구가 공개 근거로 검토한 30개 구성 중 L4로 판정된 사례는 없었습니다. [LACG 연구](https://www.mdpi.com/2076-3417/16/10/4788) |

Berkeley 등의 분류는 사람이 정한 목표를 구현부터 배포까지 에이전트가 맡는 것을 Level II로 부릅니다. METR의 50%·80% 시간 지표는 정해진 과제 집합에서 성공 확률을 측정합니다. 이 프로젝트는 등급 숫자와 함께 **대상 작업의 범위, 사람의 승인 지점, 실패 복구 방식**을 명시합니다. [자율 개발 책임 분류](https://rdi.berkeley.edu/blog/auto-software-dev/) · [METR 측정 방법](https://evals.alignment.org/time-horizons/)

### Family Planner의 목표와 필요한 하네스

**제품 동작이 승인된 기능 하나를 에이전트가 구현하고, 중간 작업 지시 없이 검증과 실패 복구를 거쳐 리뷰 가능한 PR까지 준비하는 것**을 목표로 합니다. 제품 결정, 첫 푸시 승인, 화면 변경의 실기기 확인은 해당 시점에 사람에게 요청합니다. 이 목표는 Shapiro의 L4에 가까운 프로젝트 목표이며, LACG 기준의 L4 달성을 입증한 상태는 아닙니다.

| 우선순위 | 하네스 | 남길 결과물 |
|---|---|---|
| 1. 기능별 완료 조건 | 기존 작업 항목에 사용자 목표, 기준 보드 버전이나 스펙 위치, 관찰 가능한 기대 동작을 붙입니다. 필요한 제품 결정이 비어 있으면 구현 전에 기록합니다. | 기대 동작과 해당 Journey·스냅샷·실기기 확인을 연결한 작업 항목 |
| 2. 실행과 판정 | 기존 영향 범위 테스트, 필요한 Journey, USB Driver를 작업에 맞게 실행합니다. 실패하면 원인을 좁히고 재실행합니다. | 대상 커밋, 명령, 통과·실패·생략과 그 이유, 재현 명령이 있는 검증 기록 |
| 3. 세션 재개 | 워크트리, 마지막 확인 커밋, 남은 실패, 다음 명령을 파일에 남깁니다. 기존 상태 보드에서 그 기록으로 이동할 수 있게 합니다. | 사용량 제한이나 세션 종료 후에도 다른 에이전트가 이어받을 수 있는 기록 |

Shopify Helix는 작은 작업 단위마다 행동 테스트, 화면 비교, 독립 리뷰와 승인을 연결합니다. Family Planner의 새 기능은 대응하는 기존 앱 화면이 없을 수 있으므로 기준을 승인된 제품 규칙과 보드에 둡니다. [Shopify Helix](https://shopify.engineering/helix) · [저장소 상태 보드](../../../tools/board/README.md)

### 첫 실험과 판정 방법

반복 일정 편집의 적용 범위가 합의되면 **내일부터 변경 → 과거 일정 유지 → 아이 홈 반영**을 첫 대상으로 삼습니다. 에이전트가 기대 동작을 테스트로 붙이고 구현과 재실행을 마친 뒤 리뷰 자료를 남깁니다. 다른 세션이 기록만으로 마지막 검증을 재현할 수 있는지도 확인합니다.

측정할 항목은 사람의 추가 실행 지시 없이 리뷰 준비까지 도달한 작업 수, 사람의 개입이 필요했던 이유, 리뷰에서 다시 열린 누락, 다음 세션의 재현 성공 여부입니다. 예정된 승인, 미정인 제품 결정, 도구·환경 문제를 구별해 기록하면 다음 하네스 투자 지점을 찾을 수 있습니다.

## 하네스 세션에 요청할 결정

1. 두 실행의 기본 fixture와 메모리 저장 동작을 어디에서 공유할까요? 이미 진행 중인 작업과 겹친다면 수정 패치에서 어떤 부분을 가져오는 게 좋을까요?
2. 기존 실기기 UI 테스트 계획과 별개로, USB JSON Journey 두 개를 드라이버 변경 시 실행하는 가벼운 확인 절차로 둘까요?
3. 첫 수정에서 외부 클라이언트 주입과 실패 증거까지 맞추고, 공유 fixture 구조와 HTTP 차단은 후속 작업으로 두는 범위가 적절할까요?
4. 변이 테스트는 PR 단위의 검출 증거부터 남기고, UX는 반복 일정 변경 흐름을 디자인 세션과 함께 검토하는 순서가 적절할까요?
5. 승인된 흐름 하나를 대상으로 완료 조건과 검증 기록을 먼저 연결하고, 다른 세션이 그 기록만으로 이어받는 실험을 할까요?
